How I Expect the Developer to Use This Build Book
I wrote this as the single source of truth to build Sarmaya OS across all variants. I do not want ad-hoc interpretation. If something is ambiguous, the developer logs it in the Decision Register and proposes the best default implementation.
Non-Negotiables
Configuration-first: policies, thresholds, approval matrices, and module toggles must be editable without code deploys.
Workflow-first: every business process is a state machine with explicit states, transitions, and audit evidence.
Strict auditability: immutable audit trail on every action, policy evaluation snapshot, and evidence pack integrity hashing.
AI is gated: structured JSON only, schema validation always, human-in-the-loop when risk or confidence thresholds require it.
Enterprise ready: deploy-per-client is the primary deployment model, but the code must remain multi-tenant compatible.
Definition of Done for Any Variant
All workflows implemented with state machine definitions, transition guards, SLAs, and escalation rules.
All policy checks implemented with a versioned rules schema and deterministic outputs.
Decision Inbox supports every work item type in that variant.
Reports and dashboards for that variant shipped and validated against seed dataset.
Integration connectors implemented with retries, idempotency, dead-letter queues, and reconciliation records.
Test pack: acceptance tests (Given/When/Then), regression checklist, and performance smoke tests.
Admin Console: configuration screens, job monitor, error monitor, and audit viewer.
Product Positioning I Am Building Toward
Sarmaya OS is a governance-first Ops OS that connects Finance, Procurement, HR, Supply Chain, and Operations with one decision surface. I am not building a generic ERP clone. I am building an operating layer that makes policies executable, evidence traceable, and decisions explainable.
Core Differentiators
Decision Inbox: one inbox across all departments for approvals, exceptions, missing evidence, mismatches, reconciliation breaks, and AI reviews.
Live Audit Mode: any transaction opens as a full timeline with policy reasons, evidence, and who did what.
Restricted Autopilot: optional, constrained to low-risk paths, always reversible, always logged, and always explainable.
Cross-department handoffs as primitives: procurement to receiving to AP to treasury is a single chain, not separate tools.
Competitive Feature Map and Where We Win
Tipalti / Payhawk / Ramp class tools: strong payments UX and vendor onboarding, but weak cross-department process chaining and control evidence packs. We win by making policy and audit the product, not an afterthought.
Coupa / Ariba class tools: strong sourcing and cataloging, but heavy and slow to tailor. We win with configuration-first policies, faster integrations, and a unified Decision Inbox across all variants.
Esker / Yooz / AvidXchange class tools: strong invoice capture and matching, but limited governance transparency. We win with Live Audit Mode, explainability traces, and deterministic policy snapshots.
Sage / Oracle / Dynamics class ERPs: broad ERP coverage, but approvals and exception handling are often clunky. We win by layering an operating system on top that makes decisions, exceptions, and evidence fast to resolve.
ServiceNow / Jira ITSM: strong ticketing, but not finance-grade governance. We win by applying the same audit + policy discipline to IT, ops, and access workflows.

Suggested Technical Stack Defaults (Editable)
These are best-in-class defaults. The developer can swap components if a client environment forces a different choice, but the product principles must remain: workflow-first, policy-first, audit-first.
Backend: Python (FastAPI) with Pydantic schemas for every API and workflow payload. Prefer a modular monolith first; split into services only when needed.
Workflow engine: Temporal as default (strong retries, idempotency, long-running workflows). Option: Camunda 8 if a client requires BPMN modeling.
Policy engine: Open Policy Agent (OPA) with versioned Rego policies. Store every decision snapshot for audit reproducibility.
Event bus: NATS JetStream for internal events (fast, simple). Option: Kafka for very high throughput deployments.
Database: Postgres as system-of-record. Add pg_partman + partitioning for audit tables. Optional: read replica for heavy reporting.
Search: OpenSearch for audit/event search and document metadata search. Optional: Postgres FTS for smaller deployments.
Object store: S3-compatible storage (AWS S3, MinIO). All files hashed; evidence packs are immutable.
Identity & access: OIDC/SAML with Keycloak by default. Support Microsoft Entra ID and Google Workspace SSO. Enforce RBAC + SoD in app logic.
Secrets: AWS Secrets Manager or HashiCorp Vault (never in DB).
OCR / document parsing: default to Google Document AI or Azure Document Intelligence (Form Recognizer). Fallback: Tesseract for simple scans.
Vector store (Copilot): Qdrant (self-host) or pgvector for smaller clients. Keep embeddings and retrieval scoped per tenant.
Reporting: Metabase or Apache Superset for v1 dashboards. Support Power BI via a reporting mart or direct connectors.
Infra: Docker + Terraform. Run on AWS ECS/Fargate for speed; graduate to Kubernetes (EKS) for larger clients. Use IaC for every environment.
Observability: OpenTelemetry, Prometheus/Grafana, Loki, Sentry. Alert on workflow stuck states, integration failures, and policy override spikes.
CI/CD: GitHub Actions with environment promotion gates. Database migrations are versioned and reversible.
Core Data Boundaries

Evidence store: immutable files plus extraction metadata, linked to transactions.
Audit log: append-only events table, optionally streamed to external SIEM.
Reporting mart: read-optimized tables or warehouse sync for dashboards.
Security, Compliance, and Audit
Audit Trail Requirements
Every user action emits an AuditEvent with actor, action, entity, before and after diff, timestamp, correlation_id.
Every policy evaluation is stored with policy_version, inputs snapshot, output decision, and reasons.
Every approval includes rationale text, outcome, and attached evidence if required.
Every document stored with content hash. Evidence pack includes hashes of all attachments referenced.
Access Controls
RBAC with scopes: tenant, business unit, location, cost center, project.
SoD enforcement: maker-checker and restricted combinations of roles.
Field-level masking for sensitive fields where needed (bank accounts, national IDs).
Auditor role: read-only access plus audit export.
Operational Security
Secrets management: environment injected, never stored in DB.
Encryption at rest for DB and object store; TLS in transit.
Backups: daily full, hourly incrementals where feasible. RPO and RTO documented per client.
Immutable audit: guardrails to prevent hard deletes; soft delete for business objects only.
Process Engine Specification
State Machines
Every workflow is defined as a state machine with explicit states, transitions, guards, and side effects. I want these definitions stored as versioned JSON per workflow, so I can audit and evolve processes per client without code rewrites.
State Machine JSON Template
{
  "workflow_key": "finance.invoice.matching",
  "version": "1.0.0",
  "states": [
    {"key": "draft"},
    {"key": "submitted"},
    {"key": "policy_check"},
    {"key": "match_attempt"},
    {"key": "exception_queue"},
    {"key": "approval_pending"},
    {"key": "approved"},
    {"key": "rejected"},
    {"key": "posted"},
    {"key": "closed"}
  ],
  "transitions": [
    {
      "from": "draft",
      "to": "submitted",
      "event": "submit",
      "guards": ["has_required_fields", "has_min_evidence"],
      "effects": ["create_work_item", "emit_audit_event"]
    }
  ],
  "sla": {
    "approval_pending": {"hours": 48, "escalate_to": "approvals.manager_queue"}
  }
}
Work Item Types
ApprovalTask: approve or reject with rationale.
ExceptionTask: resolve mismatch, missing evidence, or policy violation.
ReviewTask: HITL review for AI extraction or AI-suggested decisions.
ReconciliationTask: resolve bank or ledger breaks.
AdminTask: configuration change approvals, policy change approvals.
SLA, Escalation, Delegation
SLA timers start when a task enters a state. Escalation creates a new task or reassigns based on configured rules.
Delegation supports temporary assignment of approvals and tasks with start and end dates.
Escalations must preserve original approver chain for audit.
Policy and Controls Engine
Rule Categories
Approval thresholds by amount, category, vendor risk, and department.
Tolerance thresholds for 2-way and 3-way matching (price, quantity, amount).
Vendor restrictions: blacklist, watchlist, required due diligence.
SoD: maker-checker, conflict combinations, bank change approvals.
Mandatory evidence rules: specific docs required per workflow stage.
Exception routing: where mismatches go, who resolves, and escalation paths.
Policy Rule Schema Template

  "policy_key": "finance.approval.thresholds",
  "version": "2025-12-16",
  "rules": [
    {
      "if": {"amount_gte": 5000, "currency": "USD"},
      "then": {"route_to": "approvals.finance_manager", "min_approvals": 1}
    },
    {
      "if": {"vendor_risk": "high"},
      "then": {"route_to": "approvals.controller_queue", "min_approvals": 2}
    }
  ],
  "outputs": {
    "decision": "approve_route",
    "reasons": ["..."],
    "required_evidence": ["..."]
  }
}
SoD Enforcement
Requester cannot approve own request above a configurable threshold.
Same person cannot create vendor and approve vendor activation unless explicitly allowed.
Same person cannot change vendor bank details and approve the first payment after change.

Outputs include predicted changes in approval volume, exception volume, SLA risk, and autopilot eligibility.

AI Orchestration and Copilot
AI Principles
No free-form outputs in production paths. Everything is strict JSON validated against schemas.
AI never finalizes high-risk decisions without human confirmation.
AI must always attach an explainability trace: what signals were used and why it suggested an outcome.
Prompt and model versions must be stored with every AI output for reproducibility.
AI Router
Rules-based routing first: cheap models for extraction and classification, stronger models for reasoning, optional frontier model for complex unstructured text.
Fallback logic when AI fails schema validation or confidence is low.
A/B evaluation harness for prompts and models.
Copilot Capabilities
Explain exceptions: summarize mismatch and propose next steps.
Suggest coding: category, GL, cost center, project based on history and policy constraints.
Draft messages: vendor missing docs email and internal clarification requests (editable, not auto-sent).
Approval brief: auto-generate an approver summary that highlights key facts, risks, and policy results.
Policy Q&A: answer user questions about policies and SOPs using approved policy text only.
HITL Triggers
Amount above threshold.
Vendor risk high or watchlisted.
Extraction confidence below threshold.
Policy conflict detected or missing mandatory evidence.
Anomaly detection triggers: duplicates, outliers, unusual vendor bank changes, unusual timing.
Restricted Autopilot
Autopilot is opt-in per client and per workflow.
Autopilot applies only to low-risk items where all policy checks pass and evidence completeness is 100 percent.
Every autopilot action produces an audit event, a policy snapshot, and a reversible action record.
Autopilot guardrails: max daily count, max amount, and random sampling for human review.

Cross-Department Orchestration
Handoff Patterns I Require
Procurement to Finance: PR, PO, GRN, Invoice, Payment as one chain.
HR to Finance: payroll changes and postings, reimbursements, cost allocations.
Supply Chain to Finance: receiving and inventory adjustments that affect matching and accruals.
Ops to all: incident tasks can spawn approval tasks and evidence requests.
Universal Correlation IDs
Every transaction chain carries a correlation_id that links every record across modules.
Search must support correlation_id to reconstruct entire story instantly.

Golden Flows List (Minimum)
Finance: PO to GRN to invoice to match to payment to reconciliation.
