4. REQUIRED BEFORE / AT PRODUCTION
===============================================================================

Not deployed anywhere yet. When deploying:

a) SMTP_ENABLED=true plus the SMTP_* settings.
   While false, messages are HELD untouched rather than attempted, so
   switching it on later sends the backlog rather than finding it expired.

b) A scheduler running the drain, every minute is fine:
       python -m scripts.dispatch_notifications
   Without it, messages queue forever and nobody is told anything.
   render.yaml defines this as the "sarmaya-notifications" cron service.

c) Run the verifier after deploying. It fails if the queue stalls, if the
   app connects as a superuser (bypassing RLS), if DEBUG is on, or if
   self-registration is open:
       python -m scripts.verify_deployment https://... --database-url ...

d) Frontend needs NEXT_PUBLIC_API_BASE_URL pointed at the deployed API.

Never verified anywhere: real SMTP transmission. No mail server exists in
the dev environment, so delivery is tested only at the _deliver boundary.
Watch GET /api/v1/notifications/queue?status=failed on the first deploy.

                             accepting an authorising action from Slack's
                             servers collides with every SoD rule (self-
                             approval, maker-checker, first-payment-after-
                             bank-change). Outbound is small; interactive
                             approval is a project with a new auth surface.

OCR in the background        Upload currently calls an external OCR API
                             inside the request, so the user waits on a third
                             party. Moving it off is right, but it is not a
                             drop-in: it needs a processing state on the
                             invoice and a UI that reflects it, because today
                             the upload returns the extracted invoice.

WHAT THE CORE ACTUALLY HAS  (for context, not a to-do)
===============================================================================

Hash-chained immutable audit trail with integrity verification.
Segregation of duties that refuses real people: self-approval, maker-checker
  on payment release, self-reconciliation, bank-change approval, and the
  first payment after a bank change — the last three with no admin exemption.
Vendor bank change control: dual approval + cooling period + payments held
  to both accounts while open.
Field-level masking of account numbers by role, across all three surfaces
  that carry them.
Soft deletes with a mandatory reason, and a database-level guardrail that
  refuses hard deletes outright.
Change watchlist on bank changes, master data edits and policy overrides,
  with recorded acknowledgement by a second person.
Tenant isolation with two independent locks: Postgres RLS plus
  application-level query scoping.
Restricted Autopilot bounded by the approval matrix and SoD, with revert.
Evidence packs sealed under a single hash.
